# DeepSeek Harness 编排手册 v2.0

> 这份文件回答：**怎样把 DSH 的能力用到极致**，让一个零基础用户的愿望，变成一次不跑偏、不漏项、可验收的全栈交付。
> 核心不是“多叫几个 agent”，而是：单一事实源 + 明确写作用域 + 机器门 + 证据闭环。

---

## 1. 能力地图（用在哪一步）

| DSH 能力 | 用在哪 | 要点 |
|---|---|---|
| Skill（本技能） | 全程 | 触发后先读完 SKILL.md 再动手；参考按需读，不一次灌满 |
| 12 个 `rf_*` 工具 | 全程 | 所有状态/门禁只信工具输出，不用 shell 代替 |
| `systemPrompt` 段 | 全程 | 七阶段与铁律常驻，避免长上下文丢失 |
| `/forge` 命令 | 随时 | `status` 看进度、`next` 问下一步、`check` 快检 |
| PTC / `run_code` | 批量只读、解析 | 一次并行取 status+check+blueprints；不要在里面做写操作 |
| 子代理 | 建造阶段分域 | 每个子代理一个写作用域，禁止重叠 |
| 待办 `todo_write` | 全程 | 6–10 项，随阶段更新；让用户看见进度 |
| 目标 `goal` | 多小时长任务 | 只在用户明确要“一次做完”时创建 |
| 人机回环 | 接单/发布 | 最多 1 次关键提问；发布要用户确认 |
| Web `present` | 交付 | 展示 zip/关键图/报告，不贴大段源码 |

## 2. 单代理主线（默认）

```text
rf_intake → 用户确认（可选）→ rf_new → rf_design → 写 robot.yaml/文档
→ rf_check（循环修）→ rf_verify（循环修）→ rf_trace → rf_review
→ rf_audit → rf_package → 交付
```

规则：
1. **一次读回**：每个工具调用后读 `next`/`issues`，直接做下一步，不反复问用户“继续吗”；
2. **先冻结事实源**：`robot.yaml` 的 name/slug/domains/预算/关键件先定，再并行写文档与代码；
3. **小步门禁**：每完成一个域就跑 `rf_check`，不要攒到最后；
4. **证据驱动**：没有新证据不说“完成/通过”；仿真不说“实测”；
5. **失败三次规则**：同一问题修 3 次不过，停下来说明卡点、证据、可选方案。

## 3. 多代理并行（建造阶段）

### 何时值得
- 域 ≥3 且互不依赖（如 CAD、固件、软件、文档）；
- 单代理上下文快满，或预计 >30 分钟；
- 用户明确要“团队/并行/最快”。

### 写作用域（硬约束）
| 角色 | 可写 | 禁写 |
|---|---|---|
| 架构/清单 | `forge/robot.yaml`、`forge/verify.yaml`、`README.md` | 各域源码 |
| 硬件/结构 | `hardware/`、`docs/01,02,03` | 固件/软件 |
| 固件 | `firmware/`、`docs/04` | 软件/结构 |
| 软件 | `software/`、`docs/05` | 固件/结构 |
| 仿真 | `sim/`、`docs/06` | 其他 |
| 文档/证据 | `docs/`（除已分配）、`forge/evidence.jsonl` | 源码 |

- **同一文件只能一个写者**；`robot.yaml` 只由架构角色改；
- 子代理开工前先 `rf_status`，确认当前版本与指纹；
- 子代理不得各自 `rf_new`；由主代理创建后分派；
- 合并后由主代理统一 `rf_check`/`rf_render`，避免并发写 `bom.csv`/`svg`。

### 分派提示模板
```text
你是 <域> 工程师。项目根：<abs path>。只写 <scope>，不要改其他文件。
事实源：forge/robot.yaml（只读）。需求：REQ-00x..。
交付：<文件清单>；完成后运行 <命令>，把 exit code 与关键输出贴回。
禁止：编造型号、跳过测试、声称实测。
```

### 合并顺序
1. 架构冻结 → 2. 固件/软件并行 → 3. 仿真 → 4. CAD/文档 → 5. 主代理跑全套门禁 → 6. 盲审。

## 4. PTC（run_code）用法

适合：
- 一次并行取 `rf_status` + `rf_check` + `rf_blueprints`（只读）；
- 解析 JSON、生成汇总表、对比两次 check 的差异；
- 批量改**互不重叠**的文档片段（谨慎，优先 edit）。

不适合：
- 并发 `rf_new`/`rf_render`（会争用生成文件）；
- 在代码里绕过工具直接改 `forge/evidence.jsonl`（证据必须由工具写）；
- 用 shell 替代 `rf_verify` 后自称通过。

## 5. 上下文纪律

- 大文件只读需要的段落；读完写 3–5 行摘要到 `forge/decisions.md` 或待办；
- 事实源是 `forge/robot.yaml`，不要凭记忆复述；
- 每次工具返回只保留：状态、错误码、下一步；丢弃大段日志；
- 长任务每完成一域，更新 `forge/trace.md`（工具生成），用文件当外部记忆；
- 不要把所有参考文档一次读入；按阶段读：接单 archetypes、定案 design/compliance、建造 testing、发布 release。

## 6. 人机回环

- 接单最多 1 个问题，且必须给默认值；用户不答就按默认继续；
- 只有“不可逆/花钱/安全/外观偏好”才值得打断；
- 发布前必须让用户确认真实试用证据；模型不能替用户编 manual；
- 用 `ask_user_question` 时给选项 + 推荐项，不让用户写长文。

## 7. 弱模型降级

1. 只做一个域，做完跑 check；
2. 复制蓝本文件再改，不从零写；
3. 每次只改一个文件/一个函数；
4. 不确定就查 `references/` 原文，不猜；
5. 卡住就把错误原文交给用户，并给两个可选下一步。

## 8. 失败与恢复

| 现象 | 处理 |
|---|---|
| check error | 读 rule 编号 → 查 spec/对应参考 → 修 → 重跑 |
| verify 失败 | 区分环境/代码；看 exit code 与 stderr；修后全套重跑 |
| 证据过期 | 重新 verify，不手改指纹 |
| 子代理跑偏 | 中断，收回作用域，主代理接管 |
| 上下文将满 | 写 decisions/trace，压缩历史，继续 |
| 用户改需求 | 先改 robot.yaml/需求，再重跑受影响门禁，不静默改测试 |

## 9. 反模式

- 让 5 个 agent 同时写 `robot.yaml`；
- 子代理各自建项目，最后合并目录；
- 用“我觉得可以”代替 verify；
- 先写 10 篇文档再定清单；
- 为了过 check 删测试/改断言；
- 把 Beta 说成 release；
- 发布会话里贴 2000 行代码而不给 zip/摘要。
